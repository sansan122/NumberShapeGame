## 二、地图怎么玩

这是参考《杀戮尖塔》的爬塔地图：**起点在最下面，一路往上爬到层主**。

打开 `3_run_game.bat` 后是一个 1280×720 的窗口：

| 操作 | 效果 |
|---|---|
| **鼠标滚轮** / `↑` `↓` | 上下滚动视角（镜头跟随） |
| **点击高亮的节点** | 移动过去，进入那个节点 |
| **点击远处的节点** | 不移动，而是高亮出「从当前位置到它」的完整路径 |
| `D` | **查看自己的牌组**（面板可滚动，详见第六章） |
| `S` | **存档**（弹出三个存档槽选一个，详见第七章） |
| `L` | **读档**（弹出三个存档槽选一个） |
| `M` | **回主菜单**（地图 / 节点 / 战斗都能按；死亡画面上也有提示） |
| `ESC` | 退出 |

**滚轮方向**：往上滚 = **往塔的上方看**（能看到更高的楼层）。
这条约定收口在 `MapScene.scroll_up()` / `scroll_down()` 两个方法里 ——
不要在事件层直接调 `scroll()` 传正负数：`cam_y` 变大其实是**往下看**
（画面 y = `HEIGHT/2 + (世界y - cam_y)`，cam_y 变大内容就上移），
很容易写反。踩过一次，详见第十一章第 21 条。

**哪些节点能走？** 只有**下一行**的节点，它们会带一圈**蓝色呼吸光晕**。
其余节点是暗的，点不了，点了只会给你看路径。

**地图每次都不一样。** 每开一局都是现场生成的新布局
（详见第九章「游戏的地图是运行时现场生成的」）。

### 节点图标对照

图标用的是**数学符号**，和《数与形》的主题呼应：

| 图标 | 类型 | 说明 |
|---|---|---|
| `×` | 普通战斗 | 常规敌人，掉落卡牌 |
| `◆` | 精英战斗 | 阶段化敌人，掉落遗物 |
| `=` | 休整点 | 回复生命或强化一张卡 |
| `√` | 商店 | 用金币买卡牌、遗物，或移除卡牌 |
| `?` | 事件 | 三选一抉择，带世界观文本 |
| `∑` | 宝箱 | 直接获得一件遗物 |
| `★` | 层主 | 本层最终战 |

### 路线代价（本作的差异化机制）

连线上如果有个**金色小圆圈**，说明这条边带「路线代价」——走上去要付出代价，
但代价的名字全部来自数学概念，让惩罚本身也变成一次记忆强化：

| 代价 | 效果 | 数学出处 |
|---|---|---|
| **取近似** | 跳过 2 个节点，但失去 8 点最大生命 | 四舍五入求省事，必然丢精度 |
| **开区间** | 下一个节点必为精英，但战后额外获得 1 次强化 | 开区间端点取不到 |
| **未完待证** | 目标节点类型不可见 | 条件未证，结论未知 |
| **负债增量** | 获得 1 件随机遗物，但本层所有敌人血量 +15% | 借来的量要连本带利还 |

把鼠标悬停在带代号的连线上，可以看到这个代价的完整说明和数学出处。

## 三、开场界面与三名角色

### 三个角色的数值对比

| | **演算者** | **构形师** | **解方程者** |
|---|---|---|---|
| 称号 | 数之刃 | 形之壁 | 未知之追 |
| 符号 | `∑` | `△` | `χ` |
| 主题色 | 蓝 `(24,95,165)` | 绿 `(59,109,17)` | 紫 `(150,60,150)` |
| 生命上限 | 80 | **92** | 72 |
| 起始金币 | 60 | 50 | **75** |
| 定位 | 数字卡强化 | 格挡与反伤 | 抽牌与连击 |
| 被动（已生效） | 【直感】每回合打出的第一张数字卡伤害 +1 | 【承形】回合结束时若还有未用完的格挡，下回合 +2 格挡 | 【代入】每回合抽牌阶段多抽 1 张 |

**三个被动都真的接进战斗了**，不再是卡面上的文案。
结算全部写在 `battle_scene.py` 里（按 `char_id` 判断，不额外占存档字段），
而且战斗日志会写明是哪条被动生效、生效了多少 —— 方便对账：

```
「直感」生效：本回合首张数字卡 +1 伤害
「承形」生效：+2 格挡
```

> 几个容易做错的细节，实现时都踩过：
> - **【直感】判定在 `resolve_card` 而不是 `submit_quiz`** ——
>   算对才叫「打出」。放在答题环节的话，算错一次就把直感白嫖掉了。
> - **【直感】只认数字卡**：先打一张图形卡不会把这一次用掉。
> - **【承形】看的是「点结束回合那一刻」的格挡**，不是敌人打完之后剩多少 ——
>   敌人把格挡打光，也照样给下回合的 2 点。
> - **【代入】的第一回合也算**：起手就是 6 张，不是从第二回合才开始。

### 每个角色有独立的 10 张起始牌组

不是三个人共用一套牌。三份牌组都是 10 张，但重心不同：

| 角色 | 牌组特点 | 新增的卡 |
|---|---|---|
| 演算者 | 数字卡为主，伤害直接 | 沿用基础牌组 |
| 构形师 | 图形卡多，防御厚 | **反证**（格挡 5 + 伤害 4） |
| 解方程者 | 过牌快，连击多 | **换元**（抽 1 张 + 伤害 4）、**未知数**（伤害 6） |

### 数据定义在哪儿

三个角色都写在 `player.py` 顶部的 `CHARACTERS` 列表里，一条就是一个字典：

```python
{
    "id": "calculator",       # 存档里记的就是这个 id
    "name": "演算者",
    "title": "数之刃",
    "icon": "∑",              # 头像占位用的大符号
    "color": (24, 95, 165),   # 主题色：头像框、卡片高亮都用它
    "hp": 80,
    "gold": 60,
    "theme": "数字卡强化",
    "desc": "……",             # 卡片上那段定位说明
    "deck": [...],            # 10 张卡；为 None 时用默认 STARTER_DECK
    "trait": "……",            # 被动技能文案
}
```

想加第四个角色，往 `CHARACTERS` 里再 append 一条就行，
选角色界面会自动多出一张卡（卡片是横向平均排布的，暂时按 3 张算，
加到 4 张需要顺手改一下 `CharSelectScene` 里的 `cw` / `gap`）。

### 美术资源（立绘与动作动画）

三个角色都有真实的像素立绘 + 三组动作（待机 / 攻击 / 受击）。
资源放在 `assets/chars/{角色id}/`：

```
assets/chars/calculator/
├── full.png            静态立绘（选角卡片用）
├── idle_00…07.png      待机循环（8 帧 × 100ms）
├── attack_00…15.png    攻击（播完自动回待机）
└── hit_00…07.png       受击（播完自动回待机）
```

**这些 PNG 是自动生成的**：源素材是 `人物(1)/` 里的 Aseprite 工程和 GIF
（源文件不进 git），跑一次 `tmp/prepare_char_art.py` 就拆成上面的帧序列。
为什么要在开发期先转好：pygame 不能读 GIF 动画，而打包后的 exe 又不带 PIL，
所以"拆帧"这一步只能放在开发机做，产物进仓库。

预处理的两个要点：
- **全局联合 bbox**：同一角色的静态图 + 三个动作的**所有**帧用同一个裁剪框，
  这样帧与帧、动作与动作之间坐标系一致，切换动作时角色不会跳位置
- 统一缩放到高 320px，运行时再按需缩放

**加载与播放在 `char_art.py`**：

| 情况 | 行为 |
|---|---|
| 素材缺失 / 文件损坏 | `has_art=False`，调用方退回「符号 + 主题色圆」占位，**不会崩** |
| 待机 | 循环播放 |
| 攻击 / 受击 | 播完自动回待机（连着挨打时不会重头打断） |
| 缩放 | 结果按「帧身份」缓存，不掉帧 |

三处都在用它：战斗立绘（`battle_scene`）、选角卡片（`ui_scenes`）、
地图上的像素小人（`map_scene`）。

**想加第四个角色**：素材丢进 `人物(1)/` → 在 `tmp/prepare_char_art.py`
的 `CHAR_MAP` 加一行 → 跑一次脚本 → 在 `player.CHARACTERS` 加一条数据、
`char_art._DIRS` 加一行目录映射。三处界面会自动生效。

### 角色怎么跟着存档走

存档里多了一个 `char_id` 字段（见第七章）。读档时：

- 有 `char_id` → 按它还原角色
- 老存档没有这个字段 → 兜底用 `"calculator"`（演算者），**不会崩**

## 四、点击节点之后会发生什么

走到节点上，会按类型自动进入对应的内容：

| 节点 | 进去之后 |
|---|---|
| `×` 普通战斗 | 打「几何魔像」（50 血，胜了给 28 金币） |
| `◆` 精英战斗 | 打「方程组·三元」（78 血，给 55 金币） |
| `★` 层主 | 打「不可解之影」（120 血，给 120 金币） |
| `=` 休整点 | 二选一：**回复生命**（30% 上限）或**强化一张卡**（数值 +3） |
| `√` 商店 | 3 张随机卡 + 1 件遗物。另有「花 60 金币移除一张卡」的服务 |
| `?` 事件 | 随机抽一个事件，每个事件有 3 个选项，**选择会真的改变玩家状态** |
| `∑` 宝箱 | 点开箱子，**直接获得一件随机遗物** |

### 休整点

进去是两个大按钮：

- **回复生命** — 回满 30% 最大生命（80 上限就是回 24 点），点完立刻离开
- **强化一张卡** — 进入牌库网格，点哪张就强化哪张（伤害/格挡 +3，抽牌 +1），名字会带个 `+`
  - 左下角「返回」可以退回菜单改主意

### 商店

四件商品一字排开，价格按卡牌费用算（`40 + 费用 × 20`）：

- 买的卡**直接进你的牌库**，本局后续战斗都能抽到
- 遗物买下**立即生效**
- 「**移除一张卡**」服务：付 60 金币，从牌库永久删掉一张（用来精简牌组）
- 金币不够会提示「还差多少」，不会误扣

### 事件

目前有 3 个事件，每个 3 个选项，都是**真实生效**的：

| 事件 | 选项 |
|---|---|
| **断裂的等式** | 补上缺口（-10 生命，得 1 件遗物）/ 绕过去（无事发生）/ 铭记它（最大生命 +8） |
| **未完成的证明** | 替它写完（+40 金币，最大生命 -6）/ 撕掉它（移除牌库一张卡）/ 折起收好（+25 金币） |
| **沉默的演算者** | 与它交换（-20 金币，最大生命 +10）/ 点头走过（+15 金币）/ … |

选完再点一下画面任意处即离开。

### 遗物一览

| 遗物 | 效果 |
|---|---|
| **勾股定理** | 战斗内**首次**打出图形卡，额外 +3 格挡 |
| **质数筛** | 战斗开始时，从牌库移除 1 张最弱的卡 |
| **换元法** | 每回合**第一次算错不消耗卡牌**（卡留着） |
| **对数尺** | 每回合多抽 1 张牌 |
| **约等号** | 所有伤害 +1 |
| **公理石** | 最大生命 +12 |

**六个遗物的效果都真的接上了**，而且都能指出具体在哪一行结算
（原来「公理石」和「质数筛」只是躺在遗物池里，代码里一处都没实现）：

| 遗物 | 结算位置 |
|---|---|
| 勾股定理 / 换元法 / 对数尺 / 约等号 | `battle_scene.py`，按名字判断 |
| 质数筛 | `BattleScene.__init__`，**洗牌之前**筛掉最弱的一张 |
| 公理石 | `Player.add_relic()` —— 拿到的那一刻上限和当前生命一起 +12 |

> - 质数筛必须赶在 `random.shuffle` / 抽起手牌**之前**动手，
>   否则筛掉的可能是已经抓在手上的那张，等于什么都没筛。
> - 发遗物统一走 `roll_unowned_relic()`：只抽玩家还没有的，六件集齐就折现 40 金币。
>   原来宝箱 / 商店 / 事件三处各写了一个 `random.choice(RELIC_POOL)`，
>   同一个遗物能发两次 —— 名字进了列表，效果却按名字只算一份，等于白给一件。

## 五、卡牌战斗怎么玩

打开后是一个 1280×720 的浅色窗口：

1. **点手牌选一张卡**（卡片会浮起变黄）
2. **再点一下空白处**＝决定打出这张卡
3. 这时会弹出一道题，等式右边是一条**下划线**（填空线）
4. **直接敲数字键**，输入的数字会实时显示在下划线上，光标跟随闪烁
   - 按 `退格` 删掉最后一位
   - 按 `回车` 提交（或点「提交」按钮）
5. 点右下角 **「结束回合」** 轮到敌人行动

判定结果：
- ✅ **算对了**：卡牌效果生效
- ❌ **算错了**：这张卡**直接进弃牌堆**，白白浪费

**核心设计**：想打牌，先算对。数学不是外挂的答题小游戏，而是出牌的**前置门槛**。

### 三种题型（出牌方式决定题目）

| 怎么出牌 | 出什么题 | 答对之后 |
|---|---|---|
| 数字卡**单独**打出 | 算术题（加减乘） | 这张卡生效 |
| 图形卡**单独**打出 | **认图形名称**（四选一） | 这张卡生效 |
| 数字卡 + 图形卡**组合** | **算图形面积** | **两张卡一起生效**，另多抽 1 张牌 |

**组合怎么操作**：点一张数字卡（卡会浮起，底部提示「再点图形卡＝组合」），
再点一张图形卡 —— 直接进面积题；反过来先点图形卡也一样。
组合的费用是**两张卡费用之和**，能量不够时不出题、也不扣能量。

面积题里的图形**按真实比例画**（底 6 高 4 看着确实是扁的），尺寸标在图上，
公式写在题面（不用背公式）：

| 图形卡 | 图形 | 面积公式 |
|---|---|---|
| 三角盾 | 三角形 | 底 × 高 ÷ 2 |
| 方阵 | 正方形 | 边长 × 边长 |
| 镜像 | 长方形 | 长 × 宽 |
| 反证 | 平行四边形 | 底 × 高 |
| 换元 | 梯形 | （上底 + 下底）× 高 ÷ 2 |
| 归零 | 圆 | 半径 × 半径 × 3（π 取 3） |

- **数字卡上的那个数就是图形上的主尺寸**（底 / 边长 / 长 / 半径）——
  这是「数形结合」四个字的字面意思：数变成形，形再算回数。
- 另一维随机，但保证**面积一定是整数**（三角形 / 梯形的高取偶数）、
  且 ≤ 9999（输入框只有 4 位数字）。
- 认图形题是**四选一**而不是手打中文 —— 720p 窗口里敲中文不现实。
  点选项 或 按 `1`~`4` 选，`回车`提交，`退格`取消选择。

**为什么组合要补一张牌**：一次组合花掉两张卡、两份能量、只占一次出牌机会。
答对时两张卡同时生效之外再多抽 1 张，否则组合永远不如拆成两回合打，
这个机制就只是个摆设。

> 图形卡上没有数字（`value` 恒为 0），所以**单出图形卡不能考算术** ——
> 题目必须跟着"这张卡能提供什么信息"来出，这就是题型分流的由来。

### 手牌类型

| 卡 | 类型 | 效果 |
|---|---|---|
| 加一 | 数字 | 造成伤害 |
| 凑十 | 数字 | 造成伤害 |
| 平方 | 数字 | 造成伤害 |
| 未知数 | 数字 | 造成伤害（解方程者专属） |
| 三角盾 | 图形 | 获得格挡 |
| 方阵 | 图形 | 获得格挡 |
| 镜像 | 图形 | 抽牌 |
| 归零 | 图形 | 清空敌人格挡 |
| 反证 | 图形 | 格挡 + 伤害（构形师专属） |
| 换元 | 图形 | 抽牌 + 伤害（解方程者专属） |

每张卡在卡面中部都有一张**几何图案**（画法见下一节）。
图形卡另有第二种用途：和数字卡组合出**面积题**（见上一节）。

### 卡牌图案与敌人形象（`art_shapes.py`）

卡面和敌人**没有任何图片素材**，全是代码画的几何图形 —— 每个图案对应卡名的数学含义：

| 卡 | 图案母题 |
|---|---|
| 加一 | 粗加号，四角缀四个小点（"再加一个"） |
| 凑十 | 10 个圆点排成三角阵（1+2+3+4，三角数） |
| 平方 | 嵌套的两个正方形（x·x） |
| 未知数 | 虚线圈 + `χ` |
| 开方 | 一个根号（√），里面压着被开方的横线 |
| 三角盾 | 正三角 + 盾脊 |
| 方阵 | 2×2 四个方块 |
| 镜像 | 左右对称三角 + 中间虚线镜面 |
| 归零 | 圆 + 斜杠（∅ 空集） |
| 反证 | `⊥` 记号 + 交点那颗"矛盾点" |
| 换元 | 方块 → 箭头 → 圆 |

| 敌人 | 形象 |
|---|---|
| 几何魔像（普通） | 三角底座 + 方块躯干 + 菱形头（"由最基础的多边形堆成"），身体轻微呼吸 |
| 方程组·三元（精英） | 三个圆盘（各含 `χ`）连成三角互相牵制，中心是还没解出来的"解" |
| 不可解之影（Boss） | 收不拢的螺旋 + 留缺口的环（"它本身就是那个矛盾"），缓慢自转 |

**为什么不用图片**：卡在战斗里只有 132×176、牌组面板里 104×142 ——
这个尺寸下插画细节全糊成一团，几何图标反而最清晰。而且卡名本身就是
数学概念，画成对应图形比画插画更"说人话"。顺带的好处：不用带图、
不用预处理、exe 体积一分不涨。

三处共用同一套图案：战斗手牌（`battle_scene.draw_card`）、牌组面板小卡
（`deck_view._draw_mini_card`）、旧原型（`test_card.py`）。图案函数按
「可用方形边长」的比例绘制，所以大卡小卡形状完全一致，只是缩放不同。

**以后加新卡**：在 `art_shapes._ICONS` 里补一条 `"卡名": 画图函数` 就行。
漏了也不会崩 —— 会画一个问号圆盘，一眼看出"这张卡还没配图案"。
图形卡还要在 `art_shapes.CARD_SHAPE` 里补一条 `"卡名": 形状`，
否则组合出面积题时会退成正方形（不崩，但题目名不副实）。

**题目图形（`draw_shape_figure`）**：面积题 / 认图形题里画的图形，
和卡牌图案共用 `art_shapes.py`。它比卡面图案多两件事：

- 按 `dims` **真实比例**绘制（底 6 高 4 就画成扁的），不是示意图形 ——
  面积题里比例不对，玩家一眼就觉得这题在糊弄人
- 标出尺寸：虚线画「高」，白底小牌写数字（压在图形线上也读得清）；
  认图形题**不标**任何数字（标了像送答案）

**卡名末尾的 `+`**：强化会给卡名加个加号（「三角盾+」），
所以查图案 / 查形状之前一律先过 `base_card_name()` 把加号剥掉 ——
不然玩家花掉一次强化机会之后，卡面图案会变成问号圆盘、组合也认不出形状。

### 战斗背景里的数学装饰（函数画在坐标系上）

战斗背景是「渐变 + 数学装饰」两层，全部纯代码绘制（`BattleScene.draw_backdrop`
与 `BattleScene.draw_math_decor`）。中间那条空档里摆着**两个完整的坐标系**，
函数曲线是在坐标轴上动的，不是飘在半空的裸曲线：

| 图 | 内容 | 怎么动 |
|---|---|---|
| 左 | **y = sin x**（正弦） | 相位随 `t_ms` 推进，整条波**横向流动**（62px/s 左右）；另有一颗「珠子」钉在 x=6.2 处随波起伏 |
| 右 | **y = x²**（抛物线） | 开口系数 `a` 在 0.075~0.175 之间**呼吸**（口大开得缓、口窄立得陡）；一颗珠子沿曲线左右扫描 |

每个坐标系自带：带箭头的 x/y 轴、每 1 单位一道刻度、单位网格（坐标纸）、
原点 `O`、轴名 `x`/`y`，图下方还有一行函数名（`y = sin x` / `y = x²`）。
曲线绘制套在 `screen.set_clip(图纸矩形)` 里，**跑到框外会被裁掉**，
不会有线头飞出去。

**图纸的四条边界是量出来的，不是拍的**（改布局前先看这四条）：

- 左 ≥ 448 —— 三个角色**全部动作帧**的立绘像素并集是 x56~444（实测），再往左会被角色压住
- 右 ≤ 886 —— 最宽的 Boss 半径 100、`E_X=1000`，最左到 x900
- 中间让开 x=640 的「对决区」中线（占 639~641）
- 上下夹在顶栏（y0~52）和地面线（y492）之间

于是能摆图纸的只有 **x448~886 / y126~274** 这一条，两个坐标系就卡在这。
漂浮符号、公式、几何图形的坐标全部提到了模块级常量
（`DECO_SYMBOLS` / `DECO_FORMULAS` / `DECO_SHAPES`），测试脚本按**同一份数据**
检查它们有没有糊到图纸上 —— 符号的漂移公式也提成了 `deco_symbol_offset()`，
所以测试能把整个漂移过程扫一遍，而不是只看一个静帧。

### 界面元素（杀戮尖塔式舞台布局）

- 左右各站一个角色：**玩家在左**（像素立绘，待机动画一直播，
  打出伤害卡播攻击动作、挨打播受击动作；没素材的角色用大号符号圆占位），
  **敌人在右**（几何形象，普通/精英/Boss 体型递增，见上一节）
- **血条和格挡徽章画在角色脚边**（脚点 y=486，血条顶边 y=494），
  脚下有椭圆影子把角色「钉」在地面上
- 敌人**意图**（下回合要干什么，提前告诉你）悬在它头顶
- 左下角：**能量球**（当前/上限）+ **抽牌堆**；右下角：**结束回合**按钮 + **弃牌堆**
- 手牌在底部居中，牌多时自动**向中间叠起来**（牌不会顶到左右两角）
- 顶栏：左侧是角色名·称号，右侧是金币、回合数和 `D 查看牌组` 提示

### 一回合的结算顺序（格挡为什么必须留到敌人出手）

这块原来有个要命的 bug：`end_turn()` 在**敌人出手前**就把 `p_block` 清零了，
于是格挡徽章照常显示、伤害却全额打在身上 —— 玩家看到的就是「防御只有显示、没有效果」。
现在的顺序是：

| 步骤 | 做什么 | 格挡 |
|---|---|---|
| 1 | 玩家出牌（算对题才生效：算术 / 认图形 / 面积） | 打出图形卡时 `p_block += N` |
| 2 | 点「结束回合」 | **保留**，一格都不动；顺手记下 `carry_block` 供【承形】用 |
| 3 | 敌人行动 | **先扣格挡再扣血**：`实际伤害 = max(0, 伤害 - 格挡)` |
| 4 | 新回合开始 | 这时才 `p_block = 0`（格挡不跨回合），随后按【承形】给 2 点 |

> 一句话：**格挡在敌人打完之后、新回合开始时清空**，而不是结束回合时清空。
> 位置错了，整套防御体系就名存实亡。

单卡和组合的**效果结算走同一个 `_settle_card()`**（遗物「约等号」「勾股定理」
和演算者【直感】只有这一份实现）—— 所以组合里的数字卡照样吃【直感】、
组合里的图形卡照样吃「勾股定理」，不会出现两套数值。

### 打完精英 / 层主之后的战利品

普通战斗只掉金币。精英和层主会再多给两样东西，
数量写在 `battle_scene.py` 的 `ENEMY_KINDS` 里：

| 敌人 | 金币 | 遗物 | 强化次数 |
|---|---|---|---|
| 几何魔像（普通） | 28 | — | — |
| 方程组·三元（精英） | 55 | **1 件** | **1 次** |
| 不可解之影（层主） | 120 | **1 件** | **2 次** |

面板分两段：先展示刚拿到的遗物（点「收下」），再进牌库网格选一张卡强化。
几个约束：

- 遗物**不会重复发**：`roll_unowned_relic()` 只抽玩家还没有的；
  六件都集齐了就折现成 40 金币（宝箱、商店、事件三处也共用这套逻辑）
- **同一张卡在一次面板里只能强化一次**（不然名字会叠成「加一++」）
- 没有可强化数值的卡（比如「归零」）不能被选中 —— 原来会白加一个 `+` 却不改数值，
  等于骗走一次强化机会
- 路线代价「**开区间**」承诺的「战后额外 1 次强化」也在这里兑现：
  数值先挂在 `player.pending_upgrades` 上（存档会带上），打赢下一场时并进上面那张表

### 血条怎么画的

`BattleScene.hp_bar()` 一个方法同时服务玩家和敌人：

| 细节 | 说明 |
|---|---|
| 位置 | **画在角色脚边**（脚点 y=486，血条顶边 y=494），像踩在地上的状态条 |
| 数字 | 血量数字**压在条里面**，不再单独占一行文字 |
| 颜色 | 按剩余比例变：>55% 绿｜>28% 琥珀｜否则红 —— 不读数字也知道危不危险 |
| 边界 | 0 血 / 负血 / 超上限 / 上限为 0 都不会崩，也不会画出格 |
| 低血 | 填充至少保留一个圆头宽度，否则残血时条会缩成看不见的一点 |
| 描边 | 数字画两层（深色偏移 + 白色），浅底深底都看得清 |

**为什么数字要放进条里**：血条要贴着角色的脚放，空间只有一条，
数字塞进条里才放得下 —— 玩家一眼就能把「血量」和「这个角色」对上。

### 角落的牌堆计数有什么意义

抽牌堆（左下）、弃牌堆（右下）画成小卡叠 + 琥珀色数量角标：
`抽牌堆 + 手牌 + 弃牌堆 = 牌组总张数`。
配合 `D` 牌组面板，出牌/弃牌对不上时能自己核对。

## 六、查看自己的牌组

### 怎么用

**任何时候按 `D`** 都会弹出牌组面板：

| 操作 | 效果 |
|---|---|
| `D` | 打开 / 关闭 |
| `ESC` | 关闭 |
| **滚轮** / `↑` `↓` | 上下翻（牌多的时候） |
| `PageUp` / `PageDown` | 翻一整屏 |
| `Home` / `End` | 跳到最前 / 最后 |
| 点面板外面 | 关闭 |
| 点右下角「关闭」 | 关闭 |

**三种场景都能开**：地图上、节点面板里（商店 / 休整 / 事件 / 宝箱）、战斗中。
在商店买东西之前想看看自己有什么牌，按一下 D 就行。

两个例外（故意的）：

- **战斗中正在答题时不响应** —— 那时候按键要留给数字输入
- **战斗结算画面（胜/负）不响应** —— 那时候按任意键都该是「离开」，
  把 D 吞掉会让玩家按了没反应，很困惑

### 面板长什么样

- 卡片**按类型排好**：数字卡（蓝框）在前，图形卡（绿框）在后；
  同类型按费用、再按名字 —— 同名卡自然聚成一堆，一眼能看出「我有几张凑十」
- 左上角圆形数字 = 这张卡要花几点能量
- 顶上写总张数 + 「数字 / 图形」各几张
- 牌多时右侧出滚动条，卡片会**裁剪**在面板内（不会画到外面去）
- **面板高度自适应**：牌少就矮一点并居中（开局 10 张不会在下面空一大片），
  牌多则撑到上限 620px 后开始滚动

### 为什么单独一个模块（`deck_view.py`）

这个功能要在**三个不同场景**里用，而它们分属 `main.py` / `battle_scene.py` /
`node_scenes.py`。如果各自画一遍，改一次样式要改三处 ——
本项目已经吃过这种亏：**玩家面板被 `map_scene.MapScene.draw_side()` 和
`main.Game.draw_player_panel()` 各画了一遍**，改前者完全没效果（后者覆盖了它），
当时排查了好一会儿。

所以这次收口：一个 `DeckView` 类，谁想用就
`deck_view.open_with(player.deck, player.char)`，然后把事件丢给 `handle()`、
把绘制丢给 `draw()`。

**而且事件处理放在 `Game.handle()` 最顶上统一做**（而不是各模式各写一份）：

```python
def handle(self, event, mouse):
    # 牌组面板是覆盖层，开着的时候优先吃掉事件 ——
    # 否则在战斗里按 ↑↓ 翻牌组会连带把战场也操作了
    if self.deck_view.open:
        self.deck_view.handle(event, mouse)
        return None
    if event.type == pygame.KEYDOWN and event.key == pygame.K_d:
        ...
```

这样「打开时不能穿透到下层」这条规则只有一份实现，不会出现
「地图上翻牌组会同时滚地图、战斗里翻牌组却没事」这种不一致。

### 顺带加的：顶栏牌堆计数

战斗画面右上角多了 `抽牌堆 N　弃牌堆 N`。单看没什么，配合牌组面板就有用了：

> **抽牌堆 + 手牌 + 弃牌堆 = 牌组总张数**

出牌、弃牌对不上时能自己核对（也是排查「卡牌凭空消失」这类 bug 的快捷手段）。

## 七、存档 / 读档

### 三个存档槽

存档不是单个文件，而是**三个槽**（`saves/save_1.json` ~ `save_3.json`），
可以同时保留三局不同的进度。

| 什么时候 | 按什么 |
|---|---|
| 地图上想存一下 | `S` → 弹出槽位列表 → 点一个槽（或按 `1`/`2`/`3`） |
| 想回到上次存的地方 | `L` → 弹出槽位列表 → 点一个有档的槽 |
| 主菜单想接着玩 | 「继续游戏」→ 同样进槽位列表 |
| 死了想回到存档点 | `L`（死亡画面上会提示，也走槽位列表） |
| 死了想从头再来 | `R`（回选角色重开；存档保留，还能 `L` 回去） |
| 死了想回主菜单 | `M` |
| 游戏中途想回主菜单 | `M`（地图 / 节点 / 战斗都能按；建议先 `S` 存一下） |
| 打完层主自动换层 | **自动存一次**（写进本局绑定的那个槽） |

槽位卡片上写着那一局的关键信息：**第几层 / 生命 / 金币 / 牌数 / 存档时间**；
存档模式下点已占用的槽会标红「覆盖」，防止手滑冲掉想留的局。
一局游戏绑定它「第一次存进的那个槽」，之后换层自动存也写到那里。

旧版只有一个 `save.json` 的存档，程序第一次跑 `list_slots()` 时
会自动把它认作「槽 1」（改名为 `save_1.json`），老玩家不丢进度。

### 存档里存了什么

```json
{
  "version": 1,                  // 格式版本，以后改结构用
  "saved_at": "2026-09-15 21:22:17",
  "seed": 485897898,             // ← 关键：地图的随机种子
  "floor_index": 1,              // 在第几层
  "current": 0,                  // 站在哪个节点
  "visited": [0],                // 这层走过哪些节点
  "player": { "max_hp": 80, "hp": 63, "gold": 175,
              "char_id": "calculator",   // ← 关键：玩的哪个角色
              "relics": [...], "deck": [...] },
  "map_effects": { "hide_next": true, "enemy_hp_mult": 1.32 },
  "floor_stats": {}
}
```

### 为什么地图不用整个存下来？

因为地图是「**种子 → 地图**」的确定性函数：**同一个种子跑出来的地图一模一样**。
所以存档只要记住 `seed`（一个数字），读档时重新生成一遍就行 ——
存档文件因此只有 **2~3 KB**，而不是几十 KB。

读档时具体走的是 `save_system._regenerate_map(seed)` →
`build_map.build_in_memory(seed=seed)`，**按存档里的种子把地图原样重建**。

> ⚠️ 这里有个曾经的**假种子 bug** —— 打印出来的种子复现不出它生成的地图，
> 导致读档地图变样。已在避坑记录第 15 条详述，这里不再重复。

**降级路径**：万一存档里**连 `seed` 字段都没有**（很老的存档），
程序会退回读静态 `out/map.json`，只恢复玩家状态 + 楼层 + 站位。
**血和牌不会丢。**

### 容错设计（都有测试覆盖）

| 情况 | 表现 |
|---|---|
| 存档不存在，按 `L` | 提示「读档失败：没有存档」，不崩 |
| 存档 JSON 写坏了 | 提示「存档损坏」，原文件改名为 `save.json.bad` 留档（不直接删） |
| 存档版本比程序新 | 拒绝加载，提示版本号 |
| 存档字段残缺 | 缺的字段用默认值补上，能启动 |
| **存档没有 `char_id`**（老档） | 兜底用 `calculator`（演算者），能启动 |
| 血量是负数 / 超上限 | 自动夹回 `0 ~ max_hp` |
| 牌库里混了坏卡 | 跳过那张坏卡，保留其余 |
| 存档写到一半断电 | 先写 `.json.tmp` 再改名，原存档不受影响 |
| 存档的种子重建不出地图 | 降级重建，只恢复状态，不崩 |

### 已知限制

- **战斗中不能存档**（按 `S` 会提示「战斗中不能存档」）。
  战斗中场面状态太多（手牌、弃牌堆、敌人意图），完整序列化成本高，
  收益却低 —— 爬塔游戏的标准做法就是只在地图上存。
- 存档是**单槽**的，再存一次会覆盖上一份。

## 八、怎么发给别人玩（打包）

### 一句话版

```
<python> 打包.py
```

跑完在 `release/数与形-公理塔.zip`（约 25 MB），**直接把这个 zip 发出去就行**。

### 对方拿到之后要做什么

**双击 `NumbersAndForms.exe`。** 就这一步 —— 不用装 Python、不用装 pygame、
不用解压到特定位置、不用联网。

（Windows 会弹一次蓝色的「已保护你的电脑」，那是没买数字签名证书的正常提示，
点「更多信息 → 仍要运行」即可。这一点已经写在给玩家的说明里了。）

### 为什么要打包，不能直接发文件夹

发源码文件夹的话，对方电脑上必须有：
① Python 3.8+　② pygame　③ 一个装有微软雅黑的系统
—— 三个条件缺一个就跑不起来。而「只会双击」的人第一个就卡住了。

打包把这三点全解决了：Python 和 pygame 打进了 exe，
字体也跟着打进去（找不到时还有降级链）。

### `打包.py` 做的五件事

| 步骤 | 做什么 |
|---|---|
| 1 | 重新生成所有 `.bat` 启动器（保证编码与探测逻辑是最新的） |
| 2 | PyInstaller 打成单文件 exe |
| 3 | 整理发布目录：只放玩家需要的东西 |
| 4 | **在隔离目录里真跑一遍**，5 秒不崩才算过 |
| 5 | **读出 exe 里的 PYZ 核对代码指纹**，确认装进去的是最新代码 |

第 4 步是关键 —— 它模拟「对方拿到手」的场景（一个新文件夹里只有一个 exe，
没有源码、没有 `data/`），能抓出「本机能跑、拷过去就崩」的问题。

第 5 步是补另一类漏子：**第 4 步只能证明「能跑」，证明不了「跑的是新代码」**。
增量构建吃到旧缓存、清理被安全策略拦下导致流程中断在半路，
都会让发布目录里躺着上一轮的 exe —— 而它照样能跑 5 秒不崩。
这一步读 PYZ 逐条核对指纹，对不上就直接中止打包，
不会安静地把旧 exe 发出去（原理和三道假信号见第十一章第 24 条）。

### 发布目录里有什么

```
release/数与形/
├── NumbersAndForms.exe     26 MB   双击即玩
├── 发给别人-怎么玩.txt        4 KB   给玩家看的说明（极简版）
├── 0_START_HERE.bat        1 KB   备用启动器（会显示报错信息）
└── 开发者文档.md            40 KB   这个 README 的副本
```

### 单文件 exe 的取舍

`NumbersAndForms.spec` 里刻意选了 **onefile**（只有一个文件）而不是 onedir：

| | onefile | onedir |
|---|---|---|
| 发给别人 | ✅ 一个文件，不会漏 | ⚠️ 一个文件夹，容易漏文件 |
| 启动速度 | 首次慢 1~2 秒（要解压） | 快 |
| 出问题排查 | 较难 | 容易 |

对「只会双击的人」来说，**一个文件**比启动快两秒重要得多。

### 想看到报错信息（调试版）

默认 exe 是**无控制台**的（`console=False`），好处是不弹黑框，
代价是 Python 的报错看不见。要排查问题就临时改：

```python
# NumbersAndForms.spec 里
console=True,      # ← 默认 False
```

重新打包，运行时就会弹一个黑框把报错显示出来。

### 三个针对打包的改造（都是必须的）

打包后 `__file__` 和执行环境都变了，有三处不改就会出问题。
全部收在 **`game_env.py`** 一个文件里：

| 问题 | 不改会怎样 | 解法 |
|---|---|---|
| `__file__` 指向临时解包目录 | **存档写进临时目录，退出即删** | `user_data_path()` → 优先 exe 同级的 `saves/` |
| 资源被解压到别处 | 读不到 `tower.yaml` | `resource_path()` → `sys._MEIPASS` |
| 别人电脑没微软雅黑 | **启动就崩** | 多级字体兜底链 + 最终退回 pygame 内置字体 |

**约定**：任何地方要用字体或路径，都从 `game_env` 拿，别再自己写
`Path(__file__).parent` 或 `"C:/Windows/Fonts/..."`。

### 重启打包（改了代码之后）

```
<python> 打包.py
```

会覆盖 `release/` 里的内容。`build/` 和 `dist/` 是中间产物，已在 `.gitignore` 里。

### 重要：游戏的地图是「运行时现场生成」的

**游戏本身不读 `out/map.json`。** 每次开新局，`Game` 初始化时会调用
`build_map.build_in_memory()` **现场生成一张新地图**（不落盘），
所以**每开一局节点布局都不一样**。

`map_tools/out/map.json` 现在的用途只剩两个：

1. 给 `map_tools\2_gen_map.bat` / `3_gen_map_random.bat` 落一份档
2. 生成 `out/map.html` 预览页，方便不开游戏也能看地图长什么样

```
build_map.py
    ├── build_in_memory(seed)  → 返回 dict（不落盘）  ← 游戏用这个
    └── build(seed)            → 调上面那个 + 写 out/map.json + 打印种子
```

生成逻辑只有一份（在 `build_in_memory` 里），两个入口共用，
不会出现「预览图和游戏里的图不一样」这种事。

**为什么要这么改**：以前 `Game` 读的是静态的 `out/map.json`，
而这个文件只在手动跑生成器时才变 —— 于是「不管运行几次，
地图节点都是一样的」。用户反馈过这个现象，根因就在这。

**存档怎么复现地图**：存档记 `seed`，读档时调
`build_in_memory(seed=存档里的seed)` 重新生成同一张图（详见第七章）。

**改生成器之后还需要重跑 `.bat` 吗？**
只是为了更新 `out/map.json` 和 `out/map.html` 的话要；**游戏本身不用**，
因为游戏每次都是现算的。但记得跑一遍抽样脚本确认分布还正常。

## 十、地图工具

运行 `map_tools\2_gen_map.bat`，会：

1. 读取 `data/tower.yaml` 里的三层塔配置
2. 生成节点与连边 → `out/map.json`
3. 画成一张 SVG 网页 → `out/map.html`，并**自动用浏览器打开**

### 想要一张新地图？

三种模式，**双击 `map_tools\3_gen_map_random.bat` 就是每次全新的地图**：

| 想做什么 | 怎么做 |
|---|---|
| **每次都不一样**（推荐） | 双击 `map_tools\3_gen_map_random.bat`，或命令行 `--random` |
| 固定那张调试用的图 | 双击 `map_tools\2_gen_map.bat`（默认种子 `20260915`） |
| 复现某张特定的图 | 命令行 `--seed 1234`，种子号会打印出来 |

生成时会打印**随机种子**，想再抽到同一张图就把它填给 `--seed`。

> 📌 **这只是「预览」用的。** 游戏自己不看这张图 ——
> 开游戏时它现生成，所以**不跑这个 `.bat` 也已经每次都不一样了**。
> 这里生成的 `map.json` / `map.html` 是给你在工作之余
> 不开游戏、用浏览器直接看地图用的。

### 节点类型怎么撒的

这一节前后改过**三版**，把演进过程记下来，免得以后又绕回去。

**第 1 版：逐行独立掷骰子 + 每 5 行指定一个「特殊行」。**

结果是**每行几乎都是「3 个战斗 + 1 个事件」**，特殊行又变成清一色
（`=休整 √商店 √商店 √商店`）。根因是普通行的候选池排除了
`rest/shop/treasure` 但**漏了 `event`**，而 `event` 权重不低，
抽 4 个位置几乎必然中一个。

**第 2 版：先按权重算整层配额，再打散撒进各行。**

修掉了上面的 bug，但引入了新的「太整齐」问题：

- 每层节点数几乎一样（实测恒定 32/35/38），因为行数固定、
  `randint(2, width)` 的期望值恒定
- 每种特殊节点数量被配额钉死，每层都是「休整 2、商店 2、事件 2~3」
- 强制「每行最多 1 个特殊节点」，特殊节点像打格子一样均匀铺开

用户的原话是「**地图随机性不行，再改改**」—— 问题不是"缺项"，
而是**方差太小**，观感上觉得每次都一样。

**第 3 版（现在）：每格独立掷骰子 + 轻量约束。**

随机性交给概率自然生长，约束只在「明显不合理」时兜一下：

1. **每行几个节点：真的随机**（1~`width`，允许只有 1 个的
   「独木桥」行，那是很好的节奏变化）
2. **每个格子：从全部类型按 `weight` 掷骰子**（含特殊节点）
3. **软约束**：同一行不出现两个同类型特殊节点；
   相邻两行不连续出同一种特殊节点；一行最多 2 个特殊节点
4. **硬兜底**：掷完之后统计每种特殊节点的总数，
   低于下限就补、高于上限就换成普通战斗

另外还做了两处「手感修正」：

- **开局第一回合必须有得选**：起点行只有 1 个节点，它连到第二行
  是按 x 位置就近连。如果第二行只有 1 个节点，那「第一回合选路」
  这个动作就不存在了。所以强制第二行 `>= 2` 个节点，
  并且把最无聊的格子换掉 —— 一个换休整点、一个换商店，
  于是开局永远是「**稳一手 or 拼一把**」。
- **连边数量也随机**：1 / 2 / 3 条按 `40% / 45% / 15%` 掷，
  原来固定 2 条看起来很规整。

实测 60 轮抽样（`map_tools/tools/sample_distribution.py`）：

| 检查项 | 结果 |
|---|---|
| 地图唯一性 | 60 / 60 张互不相同 |
| 每层节点总数 | 20 ~ 43（标准差 4.08） |
| 精英战斗数量 | 0 ~ 12（标准差 2.05） |
| 商店数量 | 1 ~ 5（标准差 1.00） |
| 缺项 | 三层 × 四类型全部出现过 |
| 扎堆（一行 ≥3 个特殊节点） | 0 次 / 2520 行 |
| 死路 / 走不到 Boss | 0 个 / 0 张 |

对比第 2 版（节点数恒定 32/35/38、精英恒定 5/6/5），
现在每层的规模、精英密度、特殊节点位置都在自然波动。

当前输出（固定种子 `20260915`）：

| 层 | 名称 | 节点 | 连边 | 带代价的边 |
|---|---|---|---|---|
| 1 | 塔基 · 数之庭 | 21 | 27 | 5 |
| 2 | 塔身 · 形之廊 | 32 | 45 | 7 |
| 3 | 塔冠 · 方程之顶 | 33 | 49 | 7 |

（用随机模式每次数量和连边都会变。）

**改完生成器要做什么？**

- **游戏不用管** —— 它每次开新局都现算（见第九章）
- 想让 `out/map.json` / `out/map.html` 这个**预览**跟着更新，
  重跑一次 `map_tools\2_gen_map.bat`
- 顺便跑一下 `map_tools/tools/sample_distribution.py` 确认分布没坏

> 历史上这里是「改完必须重跑，否则游戏里还是旧图」，
> 那个坑正是后来改成运行时生成的动机（见避坑记录第 13 条）。

## 十一、避坑记录（踩过的坑，别再踩）

### 1. `.bat` 报 `Code language not supported or defined`

**现象**：双击脚本，窗口一闪，报这行错。

**原因**：`cmd.exe` 按 **GBK** 解码 `.bat` 文件，但文件是 **UTF-8** 存的。
里面的中文变成乱码，乱码行里的 `chcp 65001` 也无法识别，于是报错。

**解决**（已在本项目全部改好）：
- `.bat` 内容**只用 ASCII 字符**（纯英文提示）
- `.bat` 文件用 **GBK 编码**保存
- **不写 `chcp 65001`**

这样在任何中文 Windows 上双击都正常，且不需要管理员权限。

> 如果以后要加中文提示，正确做法是用 GBK 编码写 `.bat`，
> 而不是改成 UTF-8 再 `chcp`。

### 2. 中文文件名的 `.bat` 引用

`测试.py` 已重命名为 `my_test.py`。
纯 ASCII 的 `.bat` 引用中文文件名会因编码不一致找不到文件，统一用英文名最稳。

### 4. `draw()` 撞名把自己覆盖掉（本轮踩的最狠的坑）

**现象**：`BattleScene` 一构造就报
`TypeError: BattleScene.draw() missing 2 required positional arguments`。

**原因**：类里有两个 `draw` ——

```python
def draw(self, n):                        # 抽 n 张牌
def draw(self, screen, mouse, t_ms):      # 画一帧
```

Python 后定义的**直接覆盖**前一个，于是 `self.draw(5)`（想抽牌）
调到了「画一帧」上，参数对不上。

**解决**：抽牌方法改名 `draw_cards()`。
**教训**：同一个类里别让「动作」和「渲染」共用 `draw` 这个名字，
渲染统一叫 `draw` / `draw_xxx`，其他动词换名字。

### 5. 布局写在 `draw` 里 → 第一帧点不到

**现象**：面板刚出现时点按钮没反应，得等一帧之后才正常。

**原因**：主循环是 `handle()` → `draw()` 的顺序。
`handle` 里要用 `self.btn_ok`，但它是**上一帧** `draw` 才创建的 ——
第一帧根本还不存在（或还是空的）。

**解决**：所有「点击判定要用到的矩形」都在 `__init__` 里算好；
如果矩形依赖运行时的状态（比如牌库变了），就在**改变状态的那一步**
同步重算，绝不放在 `draw` 里。

本项目已按这个原则改过 4 处：
`ShopPanel.item_rects` / `ShopPanel.card_rects` /
`RestPanel.card_rects` / `EventPanel.opt_rects` / `TreasurePanel.btn_ok`。

### 6. 打死敌人不结束战斗

**现象**：一刀把敌人砍到 0 血，战斗却没结束，要再点「结束回合」才判胜。

**原因**：`resolve_card()`（出牌结算）里忘了调 `check_end()`，
只有 `submit_quiz()` 和 `enemy_act()` 里调了。

**解决**：`resolve_card()` 末尾补上 `self.check_end()`。
**教训**：凡是会改动血量/胜负的入口，都要过一遍结束判定。

### 7. 卡片网格排到屏幕外

**现象**：休整点一进去，牌库网格的 x 从 `-119` 铺到 `1399`，左右都出屏了。

**原因**：布局用 `total = n * cw + (n-1) * gap` 居中，
10 张卡 × 132 宽早就超过 1280，居中的结果是**两边一起溢出**。

**解决**：改成**按行折行**（`per_row = (WIDTH - 120) // (cw + gap)`），
并且只在真正进入选卡界面时才排布。

### 9. 地图「每次都长一样」

**现象**：不管重跑多少次，地图永远是「3 个战斗 + 1 个事件」，一模一样。

**两个原因，要一起改**：

**(a) 种子写死了**
`build_map.py` 里 `SEED = 20260915` 是个常量，`random.Random(SEED)`
每次都从同一状态出发 → 逐字节相同的结果。
→ 改成 `--random` 时传 `None`（用系统随机源），并且**把实际用的种子打印出来**，
方便复现。

**(b) 类型分配是「逐行独立掷骰子」**
这是「3 战斗 + 1 事件」的真正来源：

```python
elif r % 5 == 4:                     # 每 5 行硬性一个特殊行
    ntype = rng.choice([...特殊节点...])
else:
    ntype = weighted_choice(         # ← 池子里把 rest/shop/treasure 排除了
        [t for t in node_types
         if t["id"] not in ("rest", "shop", "treasure")], rng)
```

普通池里只剩 `battle`(45) 和 `elite`(15) 和 `event`(12)……
等等，`event` **不在排除名单里**，所以权重 45:15:12 抽 4 个位置，
出来的就是「3 个 battle + 1 个 event」。
特殊行更惨：第一个位置定死是特殊节点，**剩下 3 个位置仍然从排除过特殊节点的池子里抽**，
于是变成 `=休整 √商店 √商店 √商店`（一行三家商店）。

**→ 改成「先规划整层配额，再打散撒进各行」**：先按权重算好每种要几个
（各带上下限、且浮动 ±1），把它们分到**不同行**（每行最多 1 个、
尽量互相隔开），剩下的位置才填普通/精英。

**顺带一个坑**：`boss` 不在 `tower.yaml` 的 `node_types` 里
（它是层主专属），所以 `type_by_id["boss"]` 会 `KeyError`。
→ 用 `.get()` 兜一个默认值。

### 11. `handle()` 里忘记 `return`，信号全被吞掉

**教训**：这类「返回值被吞」的 bug，看代码很难发现（缩进一样、

### 15. 「报告的随机种子」必须真的能复现它生成的东西（最隐蔽的一个）

**现象**：存档 → 读档 → **地图变样了**。
而更诡异的是：`seed` 一模一样、节点总数一模一样，
**但节点类型对不上**。

排查顺序（值得记，因为前几步都是"看起来正常"）：

1. 怀疑模块被重复加载（`build_map` 被 import 了两遍，`random` 状态串了）
   → 检查 `bm2 is M.B` → `True`，**排除**
2. 怀疑 `build_in_memory(seed=N)` 同种子不确定
   → 连跑 3 次比对 → 完全一致，**排除**
3. 于是只剩一种可能：**「报告的种子」根本不是「用来播种的种子」**
   → 验证：拿打印出来的 seed 重新生成，比对原图 → **对不上**，抓到了

**根因**是这一行：

```python
rng = random.Random(seed)
used_seed = seed if seed is not None else rng.randint(1, 999999999)
```

`seed is None` 时，`rng` 是由**系统熵**播种的，
`used_seed = rng.randint(...)` 只是「从这个随机流里再抽一个数」——
**它跟 rng 的实际状态没有任何关系**。于是：

- 程序打印 `随机种子：532265712`
- 而 `random.Random(532265712)` 生成出来的是**另一张图**
- 存档里记的就是这个假种子 → 读档读到的自然不是同一张

**为什么以前没暴露**：静态地图时代，读档读的是 `out/map.json`，
根本不走种子重生这条路，假种子也就无从暴露。
**改成运行时生成之后，问题立刻浮出来了** —— 这个 bug 其实从做存档时
就存在（提交 `00a6a76`），只是躺了三个提交。

**→ 正确写法**：

```python
if seed is None:
    seed = random.SystemRandom().randint(1, 999999999)   # 先定种子
rng = random.Random(seed)                                # 再拿它播种
```

**→ 规矩**：
1. **「记录种子」要在「用它播种之前」完成**。顺序反了就拿到假种子。
2. 凡是「靠种子复现」的东西，**必须写一条测试：拿到报告的种子，
   重新生成一遍，逐字段比对**。只测「同一种子跑两次一致」是不够的 ——
   那个测试在上面第 2 步就通过了，但 bug 依然在。
   现在的 `verify_ui.py` 第 7 组专门守这条。

### 17. 打包成 exe 后，`__file__` 和「项目根」全都变了 ⚠️

**这是打包最容易踩、也最致命的一个坑**，因为它表现为
「本机跑得好好的，发给别人就崩 / 存档莫名其妙丢了」。

**三个具体症状**：

**(a) 存档写进临时目录，退出即删**
源码模式下 `Path(__file__).parent` 就是项目根，写 `saves/` 没问题。
打包后 PyInstaller 会把内容解压到 `%TEMP%\_MEIxxxxxx\`，
`__file__` 指向**那里** —— 存档写进去，程序一退就被清掉，
玩家下次打开发现存档没了（而且完全不报错，最难查）。

**(b) 读不到数据文件**
`tower.yaml` 如果没打进包，或者代码按 `__file__.parent.parent/"data"` 去找，
打包后路径算出来是临时目录里的一个不存在的路径 → 地图生成直接失败。

**(c) 别人电脑上没有微软雅黑 → 启动就崩**
`pygame.font.Font("C:/Windows/Fonts/msyh.ttc", 20)` 在字体文件不存在时
**抛异常**。自己电脑上有雅黑，永远发现不了这个问题。

**解法：所有路径和字体都收进一个 `game_env.py`**

```python
IS_FROZEN = getattr(sys, "frozen", False)   # PyInstaller 会设这个标志

def app_dir():          # exe（或项目根）所在目录 —— 用户看得见的地方
    return Path(sys.executable).resolve().parent if IS_FROZEN \
           else Path(__file__).resolve().parent

def resource_path(*p):  # 只读资源：打包后在 _MEIPASS 里
    base = Path(getattr(sys, "_MEIPASS", app_dir())) if IS_FROZEN \
           else Path(__file__).resolve().parent
    return base.joinpath(*p)

def user_data_path(*p): # 可写数据：优先 exe 同级，写不了退 AppData
    ...

def load_font(size):    # 多级兜底，最后退回 pygame 内置字体，永不抛异常
    ...
```

**→ 三条规矩**：
1. **路径只从一个地方拿**。禁止在业务代码里再写
   `Path(__file__).parent` 或 `"C:/Windows/Fonts/..."`。
   散布在 6 个文件里的 31 处字体调用，打包时会全部变成坑。
2. **区分「只读资源」和「可写数据」**。前者在临时解包目录，
   后者必须在用户看得见的地方（exe 同级 or AppData）。
3. **字体要有降级链，永不抛异常**。没有中文字体时退回 pygame
   内置字体 —— 中文会显示成方块，但**程序能跑、能点、能退出**，
   比直接崩掉强得多。

**验证方式**：把 exe 单独拷到一个**空文件夹**里跑，
检查 ① 能启动 ② 存档落在同级的 `saves/`。
`打包.py` 的第 4 步就是自动做这件事。

### 18. `.bat` 里写死本机 Python 路径，别人电脑上必然报错

**现象**：自己双击 `.bat` 一切正常，发给别人报
「系统找不到指定的路径」。

**根因**：

```bat
"C:\Users\sanji\.workbuddy\binaries\python\envs\naf\Scripts\python.exe" "main.py"
```

这条路径只存在于开发机上。

**解法**：`.bat` 里做**四级探测**，按可靠性从高到低试：

```bat
set "PYEXE="
rem 1) 项目自带的虚拟环境（如果一起发过去了）
if exist "%~dp0.venv\Scripts\python.exe" set "PYEXE=%~dp0.venv\Scripts\python.exe"
if defined PYEXE goto RUN
rem 2) PATH 里的 python
for %%I in (python.exe) do if not defined PYEXE if exist "%%~$PATH:I" set "PYEXE=%%~$PATH:I"
if defined PYEXE goto RUN
rem 3) py 启动器
where py >nul 2>nul
if %errorlevel%==0 set "PYEXE=py"
if defined PYEXE goto RUN
rem 4) 常见安装位置 ...
rem 都没有 -> 打一段英文提示（不能是中文，见第 1 条）并 exit /b 1
```

**顺带**：`.bat` 是**生成出来的**（`tools_dev/gen_bat.py`），不是手写的。
这样能保证：① 编码永远对（GBK）② 五六个 `.bat` 共用同一段探测逻辑，
改一处不会漏四处 ③ 生成时自动校验「内容纯 ASCII」。

**规矩**：`.bat` 里**永远不出现绝对路径**。
需要路径就用 `%~dp0`（脚本自身所在目录）。

### 19. 单文件 exe 的启动黑框 / 报错看不见

程序闪一下就没了，不知道错在哪。

**排查办法**：临时把 spec 里的 `console=False` 改成 `console=True`，
重新打包。运行时会弹一个黑框，traceback 就显示在那里。

**另一个办法**（不用重新打包）：程序里自己把关键信息写成日志文件。
本项目在打包自检时就是这么做的（写 `selftest.log` 到 exe 同级），
比盯着黑框看更可靠。

**注意**：`console=False` 时 `print()` 不是报错，只是输出被丢掉了。
所以代码里那些 `print` 在打包版里等于不存在 ——
真要给用户看的信息得走 `pygame` 画到屏幕上。

### 20. 环境探测写文件又删文件，会把整个程序弄死 ⚠️

这条是打包完之后才暴露出来的，而且**非常隐蔽**，值得单独记一笔。

`game_env.py` 最早判断「这个目录能不能写」的办法是**写一个探针文件再删掉**：

```python
def _writable(d):
    try:
        probe = d / ".write_probe"
        probe.write_text("x")     # 写
        probe.unlink()            # 删 ← 问题在这
        return True
    except OSError:               # ← 只拦了 OSError
        return False
```

看起来天衣无缝，实际有两个问题叠在一起：

**问题一：删文件抛的不是 `OSError`，而是 `SystemExit`。**
运行环境里有一层「删除保护」，删文件删多了（本回合累计超过 50 个）会直接
抛 `SystemExit(1)`。而 `SystemExit` 继承自 **`BaseException`**，不是
`Exception` 的子类 —— 所以 `except OSError` **根本拦不住它**。
结果就是：探针一写、一删、整个 Python 进程当场退出。

**问题二：这个探测在 import 阶段就被调用。**
`describe_environment()` → `user_data_path()` → `_writable()`，
只要有人 import `game_env` 就会跑。于是五个测试脚本、以及游戏本身，
全部**在 import 那行静默死掉**，屏幕上什么报错都没有
（打包版连黑框都没有，更难查）。

**症状**：明明代码没错，一运行就秒退，exit code = 1，没有任何 traceback。

**修法**（两条都要做）：

```python
# 1) 不用「写+删」探针，改用静态权限判断，不产生任何文件
def _writable(d):
    try:
        if not d.is_dir():
            return False
        return os.access(str(d), os.W_OK)
    except (OSError, ValueError):
        return False

# 2) 兜底要 catch BaseException（含 SystemExit / KeyboardInterrupt），
#    环境探测出任何意外都不能让游戏起不来
try:
    if _writable(primary):
        return primary.joinpath(*parts)
except BaseException:
    pass
return (Path(os.environ.get("APPDATA") or Path.home()) / "数与形").joinpath(*parts)
```

**由此得出一条通用规矩**：

> 凡是「为了探测环境」而做的小动作（写文件、删文件、起子进程、读注册表），
> 外面一律包 `except BaseException`。这类代码的定位是**尽力而为**，
> 失败时的正确行为是**安静降级**，绝不是把整个程序带崩。

顺带一个好处：改用 `os.access` 之后，exe 同级目录里不会再冒出
`.write_probe` 这种垃圾文件了（以前每跑一次都会留下 / 删掉一个）。

### 21. 滚轮 / 方向键写反了：别在事件层直接传正负数

用户反馈「鼠标滚轮的逻辑反了」。一看确实是反的，但**根因不是符号写错**，
而是**在事件层直接操作了一个方向不直观的量**。

链条是这样的：

```python
# map_scene.py
def world_to_screen(self, wx, wy):
    return int(WIDTH/2 + wx), int(HEIGHT/2 + (wy - self.cam_y))
```

`cam_y` **变大** → 所有内容的屏幕 y 变小 → 内容整体**上移** →
我们看到的是塔的**下方**。

也就是说：

| 操作 | 应该 | 原来写的 |
|---|---|---|
| 滚轮上滚 / `↑` | 往塔的**上方**看 → `cam_y` **变小** | `scroll(+y)` → cam_y 变大，反了 |
| 滚轮下滚 / `↓` | 往塔的**下方**看 → `cam_y` **变大** | `scroll(-y)`，也反了 |

**修法不是把符号翻过来**（那样下次还会写反），而是给滚动画两个
**语义化的名字**，把方向约定收口在一处：

```python
def scroll_up(self, amount):
    """视野往塔的上方走（能看到更高的楼层）。"""
    self.scroll(-amount)

def scroll_down(self, amount):
    """视野往塔的下方走（能看到更低的楼层）。"""
    self.scroll(amount)
```

调用方从此只写 `scroll_up(70)` / `scroll_down(70)`，
**不需要也不应该再自己推 cam_y 的正负**。

> **教训**：凡是「正方向不直观」的量（相机、坐标变换、缩放、旋转），
> 都别让调用方直接传带符号的数字。包一层语义化方法，
> 把「哪个方向对应哪个符号」这个知识点**只写一遍**。
> 这个 bug 之所以能活到现在，就是因为有三处调用各写各的 `scroll(±n)`，
> 每处都得重新推一次。

**验证手法**：这种 bug 在**事件层**，所以不能只调 `scroll_up()` 自证
（那只能证明方法对，证明不了接线对）。必须**投真事件**进主循环：

```python
wheel(g, 1)          # 投一个真的 MOUSEWHEEL y=+1
assert g.map.cam_y < y0     # 往上看 -> cam_y 变小
```

`verify_scroll_deck.py` 第 1 组就是干这个的，滚轮和 `↑↓` 四条线全覆盖。

### 22. 条件断言会让测试「看起来全绿」，其实没测到 ⚠️

修完上一轮的代码，顺手跑回归，结果发现 `verify_save` 的通过项数
**在 52 和 54 之间飘**。FAIL 一直是 0，所以肉眼看着完全正常。

原因在这一段：

```python
n = first_reachable(g)
if n:
    g.enter_node(n)
    if g.mode == "battle":          # ← 靠运气
        check("战斗中拒绝存档", ...)
        check("拒绝时有提示", ...)
```

地图是**每局现生成的**，贪心走一步不一定踩到战斗节点。
实测跑 8 次，**只有 1 次**真的走进战斗 —— 也就是说
「战斗中不能存档」这条规则有 **7/8 的概率根本没被验证**。

**这比测试失败更危险**：失败至少会报警，这个只会安静地少测两条。

**修法**：不要靠「走一步看看能不能碰到」，**直接把状态摆出来**：

```python
g.mode = "battle"
g.battle = BattleScene(g.player, enemy_kind="battle")
check("战斗模式下拒绝存档", g.save_game(quiet=True) is False)
check("非战斗模式下可以存档", g.save_game(quiet=True) is True)   # 反例！
```

第二条反例很重要：只断言「战斗中一定拒绝」，一个「永远拒绝存档」的
错误实现也能通过。加上反例才算真的验证了条件分支。

修完连跑 6 次，稳定 55 项。

> **两条规矩**：
> 1. **别在测试里写「如果碰到了就测」**。要么把状态摆成确定的样子，
>    要么跳过并**打印一句说明**（至少能看见漏了什么）。
> 2. **同一个坑我在同一轮里又犯了一次** —— 新写的
>    `verify_scroll_deck.py` 里「进节点模式」那条也是假设
>    「第一个可达节点不是战斗」，随机失败了一次。
>    修法是 `nd["type"] = "rest"` 把类型钉死。
>    **凡是依赖随机生成物的断言，都要显式指定它依赖的那个属性。**
>
> 顺手加的一个自检习惯：**跑完回归，把各脚本的通过项数记下来对比**。
> 项数变化（哪怕 FAIL=0）就是有断言没跑到，值得追。

### 23. 给滚动测试补断言，顺手挖出一个「滚到顶就空屏」的真 bug ⚠️

第 21 条把滚轮方向收口成 `scroll_up()` / `scroll_down()` 之后，
这轮我给它们补了几个方向断言。写断言时想顺手验一下「滚到顶会停在哪儿」，
一打印就发现不对劲：

```
滚到顶  cam=-1768 | 屏内 1/12 行   最高行屏幕y=720（贴在最下沿）
滚到底  cam= 216  | 屏内 2/12 行
```

**滚到顶只剩 1 行在屏幕里，而且那行还卡在屏幕最下边。**
根因在 `clamp_camera` 的边界符号推反了：

```python
# 旧写法（错）
top = row_nodes[-1][0]["wy"]        # 顶层，wy 最小
bot = row_nodes[0][0]["wy"]         # 底层，wy 最大
lo = top - HEIGHT * 0.5             # ← 注释写「能看到顶层」，实际把顶层推到屏幕下沿
hi = bot + HEIGHT * 0.30            # ← 同理，方向反
```

为什么容易推反：`wy = -(row * ROW_H)`，**往上爬 wy 越来越小**，
而屏幕公式是 `画面y = HEIGHT/2 + (wy - cam_y)`，
所以 `cam_y` 变**大** = 内容整体上移 = 看到塔的**下方**。
「往上看」和 `cam_y` 的正方向是相反的，`lo` / `hi` 谁配哪一端特别容易记混。

**修法：不要另写一套边界公式，直接复用 `camera_for()`**——
它就是「走到那一行时镜头该停的位置」，拿它当上下界，
等于保证「无论怎么滚，镜头落点都和正常行走时的构图一致」：

```python
lo = self.camera_for(self.row_nodes[-1][0])   # 顶层构图
hi = self.camera_for(self.row_nodes[0][0])    # 底层构图
```

**顺手验了一下修复效果**（`tmp/render_cam_extremes.py` 渲染两张图肉眼确认）：

| | 旧边界 | 新边界 |
|---|---|---|
| 滚到顶可见行数 | 1 / 12 | **4 / 12** |
| 滚到底可见行数 | 2 / 12 | **3 / 12** |

又扫了 300 张随机地图，确认「两端都不少于 3 行」是硬几何性质、不是运气：

> 行数恒为 12，可滚跨度恒为 1408，滚到顶最少 4 行、滚到底最少 3 行。

**同一个函数里还有个只写错注释、没写错代码的地方**：
`camera_for()` 的注释说「让节点落在 anchor 比例处 → 节点在下部」，
但把公式代进去化简是 `画面y = HEIGHT * (1 - anchor)`，
`anchor=0.62` 实际落在 **y≈274（屏幕上部）**，和注释说的正好相反。

**这里我选择只改注释、不改代码**，因为改成注释描述的构图，
虽然起点更饱满，但爬到顶层时 boss 会沉到屏幕下半部、上面空出一大片，反而更差。
现在的构图是两端折中的最优解。不过为了防止后人「照着错注释改符号」，
我把真实关系写成断言钉住了：

```python
for a in (0.30, 0.50, 0.62, 0.90):
    check("camera_for(anchor=%.2f) -> 节点在 y=%d" % (a, MS.HEIGHT * (1 - a)), ...)
```

> **两条经验**：
> 1. **注释和代码对不上时，先算一遍再说谁是错的**。这次是注释错、代码对，
>    但上一处是代码错 —— 只看一眼「好像注释写得挺明白」就照着改，会踩雷。
> 2. **边界值要打印出来看，别只断言「相等」**。如果我只写
>    `assert cam == 预期值` 而没打印「屏内几行」，
>    这个 bug 会一直躲在「钳制生效了」的绿灯下面。
>    属性断言（**看得到 3 行以上**）比数值断言（cam 等于某个数）更能抓住真问题。

### 24. 「exe 是新的吗」不能靠 grep，也不能靠时间戳 ⚠️

第 23 条修完相机边界、重新打完包，我顺手想确认「新代码真的进 exe 了」，
结果连踩三个坑 —— 三个坑的共同点是**都给出了看起来很有道理的假信号**。

**坑一：拿字符串裸 grep exe，永远搜不到。**

```python
data = Path("dist/NumbersAndForms.exe").read_bytes()
print("上下界直接复用" in data)      # False —— 但代码明明在里面
```

onefile 的 exe 里，PYZ 是 **zlib 压缩**过的，中文字符串当然搜不到。
我当时没意识到这点，第一反应是「是不是没打进去」，差点去重打包。
幸好我多问了一句「**这个方法本身可靠吗**」，于是拿几个
**百分之百一定存在**的字符串去试：

| 字符串 | 来源 | 裸 grep 结果 |
|---|---|---|
| `让节点落在屏幕` | `camera_for` 的旧 docstring | 无 |
| `限制相机范围` | `clamp_camera` 的旧 docstring | 无 |
| `演算者` | 普通字符串常量，游戏里满屏都是 | **无** |

连「演算者」都搜不到 —— 那问题就不在代码，在方法。

> **经验：一个检测手段在「已知为真」的样本上都报假，就先别信它的任何结论。**
> 我当时给自己的判据是：**先跑对照组**。对照组全灭 = 工具坏了，
> 不是被测对象坏了。这条现在写进了 `打包.py` 的 `BASELINE`。

**正确做法**：用 PyInstaller 自己的 reader 把 PYZ 解出来，看模块的字节码常量
（docstring 也会进 `co_consts`，所以能当指纹）：

```python
ar = CArchiveReader(str(exe))
raw = ar.extract([n for n in ar.toc if n.endswith(".pyz")][0])
tmp.write_bytes(raw[1] if isinstance(raw, tuple) else raw)
z = ZlibArchiveReader(str(tmp))
text = "\n".join(walk_strings(z.extract("map_scene")))
```

> 注意 spec 里 `optimize` 必须为 `0`。开了 `-OO` docstring 会被剥掉，指纹全失效。

**坑二：指纹必须「绑定模块」，而且必须是**从源码复制**的，不是回忆出来的。**

我第一版指纹表长这样（只有两元组，没有模块名）：

```python
FINGERPRINTS = [
    ("相机边界修复", "上下界直接复用"),
    ("camera_for 注释更正", "别再照着它改符号"),
    ("牌组面板", "按类型排序"),          # ← 两个错误叠在一起
]
```

而检查时只解了一个模块（`--module`，默认 `map_scene`）。于是：

1. 「牌组面板」这条**永远** FAIL —— 它的字符串在 `deck_view` 里，
   却拿去 `map_scene` 里找。结构上就不可能命中。
2. 更离谱的是「按类型排序」这个字符串**源码里根本不存在**，是我凭印象编的。

两条叠一起，输出是「3 条里挂了 1 条，exe 不是最新代码」——
**结论完全是错的，而它看上去特别像真的**。真去重打包只会白忙一场。

> **经验**：指纹字符串要 `grep` 出来再粘进去，不要手打。
> 而且每条指纹都得带上自己的模块名 —— 否则「搜错地方」和「代码没打进去」
> 会输出同一个 FAIL，没法区分。

**坑三：负向对照不能随便挑一个「看起来旧」的文件。**

为了证明检查器真能区分新旧，我拿 `release/_old_数与形_stale_0916113321.old/` 里的
exe 当"旧样本"。它**4 条指纹全过** —— 看起来像检查器没用。
但一看时间戳就明白了：那个目录是**一分钟前**一次失败运行留下的，
里面的 exe 恰恰是**新代码**。它根本就不是旧样本。

真正的旧样本得从**修复之前**打的那个 zip 里取（`_old_数与形-公理塔.zip`，11:04）：

| exe 来源 | 相机修复的两条指纹 | 牌组 / 血条两条指纹 |
|---|---|---|
| 11:04 的 zip（修复之前） | **FAIL, FAIL** | OK, OK |
| 现在 release / zip 里的 | OK, OK | OK, OK |

漏掉的正好是**这一轮新加的东西**，命中的正好是**上一轮就有的东西** ——
和时间线完全吻合。这才叫对照成立。

> **经验**：验证「检测器有效」的样本，必须是**你确知它旧**的样本。
> 「名字里带 old」「时间戳比较早」都不算，「符合预期地失败一次」才算。

现在这三条都以第 5 步的形式进了 `打包.py`，每次打包自动跑，
对不上就直接中止（不会安静地发出去一个旧 exe）：

```
[5/5] 内容自检：核对 exe 里的代码指纹
  对照组（必须命中，确认解析流程正常）：
    [OK  ] 解析流程基线                       限制相机范围
  代码指纹（必须命中，确认是最新代码）：
    [OK  ] 相机边界复用 camera_for            上下界直接复用
    [OK  ] camera_for 注释更正              别再照着它改符号
    [OK  ] 牌组面板高度自适应                    按卡片数量算面板高度并居中
    [OK  ] 血条随血量变色                      颜色随剩余比例变
  OK：4 条指纹全部命中，exe 里就是最新代码
```

以后每轮改完游戏代码，从新的 docstring 里挑一句加进 `FINGERPRINTS` 就行。

### 26. 「画出来给人看」的东西不会报错，只能靠像素断言 ⚠️

这一轮给卡牌和敌人加图案（全是代码画的几何图形）。两个"不报错、

**错误一：敌人浮在半空。** 原来敌人是个红圆，圆心按 `E_CY = 435 - E_R`
算 —— 圆底落在 y=435，而地面线（玩家脚底、脚下影子）在 y=486，
敌人整体浮在地上方 57px。红圆时代看不出来（圆本来就是个抽象符号），
换成有底有脚的几何形象后立刻露馅。

断言要问的是「用户看到的是否对」，而不是「代码是否按我写的算」：

```python
bottom = bbox(surf)[3] - cy                    # 形象最低那个像素离中心多远
check("底边落在脚下", 0.80 * r <= bottom <= 1.06 * r, ...)
```

**错误二：三个圆盘摆成"正品字"，重心偏上。** 精英敌人的排布角度写的是
`-pi/2`（第一个圆在正上方），实测底边只到 0.73r，看着像飘着。
改成 `+pi/2`（第一个圆落在正下方当底座）后底边到 0.88r，才"站得住"。
—— 这个如果只靠肉眼看截图，很可能觉得"还行"就放过去了。

**同类风险：图案画到卡外面 / 所有卡画成同一个图。** 复制粘贴新卡图案时
最容易漏改。用同一套像素手法钉住：

```python
mask = (pygame.surfarray.array3d(surf) != 255).any(axis=2)  # 非白像素矩阵
inked = mask.sum()                       # 「画了没有」
ys, xs = np.nonzero(mask)                # 「画到哪了」（包围盒）
raw = pygame.image.tobytes(surf, "RGB")  # 「两张卡是不是同一个图」（比字节）
```

→ **规矩：任何"画出来给人看"的东西（图案、图标、布局），断言要落在像素上。**
   「函数被调用了」「没抛异常」都证明不了画对了。
→ 计数和包围盒用 numpy 一遍算完。逐像素 `get_at` 在 400×400 上要 16 万次
   调用，慢到没法用。

**顺带两条**：
- 图案按「可用方形边长」的比例绘制（不写死像素），所以同一张卡在战斗大卡
  （132 宽）和牌组小卡（104 宽）上形状完全一致，只是缩放不同。
- 没配图案的卡名必须走**兜底**（问号圆盘），不能静默留白 —— 否则以后加了
  新卡忘了配图，卡面一片白，还会被当成布局 bug 去查。

### 27. 给背景加坐标系：先量「空档」在哪，再决定图纸摆哪 ⚠️

背景里原来有两条**悬空漂着的裸曲线**（正弦、抛物线），看着像随手画的。
这一轮给它们配上真正的坐标系（带箭头的轴、刻度、单位网格、原点 `O`、
轴名、图注）。踩到的几个点：

**一是"有地方摆"不等于"有地方看得见"。** 一开始按「中央 x340~940 是空的」
就把图纸摆上去了，结果正弦的左翼（x368~444）整个压在玩家立绘下面 ——
立绘画布是 388px 宽（444×320 的帧缩到高 280），实际有像素的位置一直铺到 x444。
所以边界不能用"大概"的，得**量**：

```python
# 三个角色 × 全部动作帧，把每帧非透明包围盒映射回屏幕坐标，取并集
bb = frame.get_bounding_rect()
L = min(L, P_X + (bb.left - fw / 2.0) * s)   # s = 280 / fh
# → 实测并集 x56~444 / y206~486，这条断言直接写进 verify_bg_decor.py
```

最后能摆图纸的只有 **x448~886 / y126~274** 这一条（右边还要给 Boss 留到 x900、
中间要让开 x=640 的对决区中线）。

**二是"曲线在动"要用整条波来验，不能钉一列看。** 第一版测试固定一列
取曲线高度，跑半周期只有 35px 变化（理论 68px），看着像"没动够"——
其实那一列正好采在节点附近，`sin(x−φ)` 在节点处对 φ 最不敏感。
两个修法一起用：
- 固定列必须**跑满一个周期**，否则可能正好采在节点上；
- 更本质的是验「整条波右移了多少」：把两个时刻的曲线高度剖面做
  **互相关**，最佳平移量应等于 `unit × Δt / 620`（实测误差 < 1px）。

```python
s, err = best_shift(sine_profile(0), sine_profile(620))
check(abs(s - B.SIN_UNIT * 620 / 620) <= 3, ...)   # 19px，实测 19px
```

**三是装饰的坐标要提成常量，测试才能跟代码用同一份真相。**
漂浮符号、公式、几何图形原来都是方法里的局部字面量，测试只能把坐标
抄一遍 —— 改代码忘了改测试，就会"测试说没事、画面已经糊了"。
现在提到 `DECO_SYMBOLS` / `DECO_FORMULAS` / `DECO_SHAPES`，
符号的漂移公式也提成 `deco_symbol_offset(i, t_ms)`，
于是测试能把**整个漂移过程**扫一遍（每 50ms 取一帧），
而不是只检查一个静帧"当前恰好没压到"。

**四是裁剪。** 曲线用 `screen.set_clip(图纸矩形)` 包住，跑出框的线头会被切掉。
一定要记得**存旧裁剪再还原**（`old_clip = screen.get_clip()`），
否则后面所有绘制都会被莫名其妙地裁掉 —— 这类 bug 的现场离原因很远，
所以断言里专门有一条：扫全屏，曲线色像素必须 100% 落在图纸内。

### 28. 「文案说了、代码没做」是一类独立的 bug ⚠️

玩家报的三件事里有两条是同一个病根：**面向玩家的效果文案早就写好挂在界面上了，
代码里一处都没实现**。翻出来的清单：

| 文案写在 | 原话 | 当时的实际情况 |
|---|---|---|
| `tower.yaml` 精英节点 | 阶段化敌人，**掉落遗物** | `ENEMY_KINDS["elite"]` 里只有一个 `gold` |
| 代价「开区间」 | 下一节点必为精英，**战后额外获得 1 次强化** | 只锁了精英，强化那半没写 |
| 代价「负债增量」 | **获得 1 件随机遗物**，但本层所有敌人血量 +15% | 只加了 15% 敌血 |
| 三个角色的 `trait` | （选角卡面底部那一行） | 纯文字，战斗里没有任何分支 |

最恶劣的是「负债增量」：罚的那半（敌人 +15% 血）实实在在生效，奖的那半没有 ——
玩家选了它等于纯亏。**一罚一奖的代价，两边都得落地。**

修完顺手立了一条自检习惯：**每写一条面向玩家的效果文案，
就立刻去代码里指出它在哪一行结算。指不出来，就是还没做。**

### 29. 格挡「只有显示、没有效果」：清算顺序错了 ⚠️

`end_turn()` 里有一行 `self.p_block = 0`，看着很合理（「回合结束了，格挡清零」），
但它排在 `phase = "enemy"` **之前** —— 敌人还没出手，格挡已经没了，
于是实际伤害永远是全额，而格挡徽章照常画在脚边。

规则本身没错（格挡确实不跨回合），错的是**落点**：
该在**新回合开始**清，不是本回合结束时清。
现在清零点挪到 `enemy_act()` 末尾（也就是新回合开头），
`end_turn()` 只负责把「点结束那一刻的格挡」记进 `carry_block` 给【承形】用。

> 这类 bug 有个共同特征：**只断言「状态对不对」是抓不到的。**
> 光调 `resolve_card()` 看 `p_block == 6` 完全正常 ——
> 必须走完整的 `end_turn() -> enemy_act()`，比**血量差分**才暴露。

### 30. 同一个文件不要并行发多个编辑 ⚠️

这轮有几次「明明提示写入成功，回头 grep 却找不到」——
原因是同一批里对**同一个文件**发了多个编辑：各自读旧内容、再各自写回，
后写的把先写的覆盖了。丢的偏偏是 `import`、函数定义这类，
症状是运行时报 `NameError`，而现场离原因很远。

**规矩**：同一个文件的改动一律串行；要批量改就写成一整个 Write。
改完顺手 grep 一遍关键符号（函数名、import），确认真的落盘了。

### 31. 界面写着「可以组合」，代码里只存了一句提示 ⚠️

玩家点数字卡，界面立刻提示「已选数字 3，可再点图形卡组合」——
而代码里那一句只是 `self.combo_hint = "..."`，**没有任何分支处理"第二次点击"**：
再点图形卡走的是"改选另一张卡"那条老路，组合永远不会发生。
玩家看到的是一句**承诺**，不是一个功能。

这和第 28 条是同一个病根，但形态更隐蔽：第 28 条那句文案挂在 YAML / 角色卡上，
这一句是**运行时现写的提示**，写提示的人和写逻辑的都以为对方做了。

规矩加一条：**提示语里出现的动作词（「再点…可以…」「按 X 可以…」），
必须能在 `handle()` 里指出对应分支。指不出来 —— 要么把它实现，要么删掉这句话。**

同轮顺手清掉一个同类隐患：`art_shapes` 查图案 / 查形状时用的是卡名原样，
而强化会给卡名加 `+`（「三角盾+」）—— 强化过的卡图案全掉成问号圆盘。
现在查表前统一过 `base_card_name()` 剥后缀。
